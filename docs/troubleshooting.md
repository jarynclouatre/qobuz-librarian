# Troubleshooting

[← README](../README.md)

| Symptom | Likely cause / next step |
|---|---|
| `The web app is using the library` | The web app holds the run lock. For a CLI run, switch to terminal mode from **Settings → Mode** (then **Resume web app** after); stopping the container with `docker compose stop qobuz-librarian` is the manual alternative. |
| `Music library unavailable` | Music bind mount unset or wrong. Check `QL_MUSIC_DIR` in `.env` and that the host path exists. |
| Container exits immediately on `up` | Usually a non-numeric `PUID`/`PGID` (a typo makes the entrypoint refuse to start) or a host bind-mount path that does not exist. `docker compose logs qobuz-librarian` shows which. |
| Downloads are off: "your music folder is mounted read-only" | `/music` is bound with `:ro`. Scans still run. Remove `:ro` from the bind in `compose.yaml` to download. |
| A volume shows **!** with "not writable by the container user" on **Settings → Diagnostics** | `PUID`/`PGID` do not match the host owner. Set them in `.env`, or chown the folder the row names, for example `chown -R $(id -u):$(id -g) ./music`. |
| Library scan says "Nothing to scan: no artist folders were found" | `/music` is mounted at an empty or one-level-off directory. `QL_MUSIC_DIR` must point at the folder that contains the artist folders, not its parent. |
| Token rejected (Save & connect) | Expired or copied with quotes. Get a fresh token from play.qobuz.com (dev tools → Local Storage → `localuser` → `token`) and paste it cleanly. |
| Token connects but downloads are disabled | Search and catalogue scans can use a token alone, but streamrip also needs the Qobuz email or numeric user ID. Add it on Settings. |
| Downloads stop with "this account can't download music" or "refused the app id and secrets" | The token works for Search and scans, but Qobuz refused the download itself: the account has no active paid subscription, or the app id and secrets streamrip downloads with are out of date. A terminal queue or a Library run stops at the first album instead of failing each one, and each queued web download fails at once with this message. For the account, check the subscription. The app id and secrets the app saved are cleared at once, so the next download fetches new ones; if they are set in your streamrip `config.toml`, empty `app_id` and `secrets` there. |
| Queued downloads say "Waiting for Qobuz" | Qobuz rejected the saved token or could not be reached as a download was starting, so the rest of the queue waits instead of failing album by album. The app asks Qobuz again every few minutes and the downloads start once it answers; **Check again** on the Queue asks now. A rejected token is replaced in **Settings**. |
| Downloads paused: "a queue … saved in the terminal is waiting" | A terminal walk or album search was stopped with albums queued that it had not started downloading. Only downloads wait, as in the terminal; scans and the other tools still run. Switch to terminal mode in **Settings → Mode**, run `docker compose run --rm -it qobuz-librarian cli` (or `qobuz-librarian` from a pip install), choose resume or discard, then **Resume web app**. |
| Downloads paused: an interrupted download "could not be cleared safely" | A download a crash or restart cuts off is settled at the next start: the partial download is removed, any tracks it set aside go back, and the album is queued again to fetch what is still missing, up to twice before it waits for **Retry**; a download as a separate copy waits for **Retry** at once. Tracks beets had already filed stay in your library, and what it left unfiled is either downloaded again or kept in **Settings → Diagnostics**. This pause means the app could not prove the state of the files, for example a staged file could not be read, another file sits where set-aside tracks belong, or the music folder was not mounted yet, which keeps set-aside tracks in their backup. Tracks it had set aside may already be back in your library; its other files were left as they were. The application log says why and names the file or folder to check; fix that, then restart Qobuz Librarian. |
| "The beets database was busy" | Another program, such as `beet web` or a backup tool, held the beets database for longer than the import waits. Retry once it has finished. |
| A download fails because staging holds files no download is using | Something outside the app's own folders is in the staging folder, such as an album folder copied in. Web downloads do not start until it is imported or moved out of staging, and a terminal download asks first or, with `--yes`, stops. A download kept by `--no-import` does not hold others back; it waits for its `beet import`, and Diagnostics names it. The files Finder, Explorer and Synology write there (`.DS_Store`, `._` files, `Thumbs.db`, `@eaDir`) are ignored. The Search page and **Settings → Diagnostics** name what is in the way. |
| **Settings → Diagnostics** lists files kept in staging | Something was set aside rather than filed: a FLAC that did not decode, a track Qobuz only served in a lossy format, a file with no usable tags, or what a stopped, cancelled or failed download, or an incomplete `--no-import` one, had already fetched. The partial download of a crash or restart is removed at the next start instead. Diagnostics names each one with its size and offers **Remove**, or **Delete anyway** when the app cannot confirm what the folder holds. A terminal run ends with one line counting them, and prints the `beet import` command for an incomplete `--no-import` download. A stopped download's copy is cleared on its own once a later attempt or the album's import holds everything in it, and a track set aside because it did not decode once the import holds all of it. |
| Stalls at "Importing into your library" | Check the job log for a failing or stalled beets plugin. Disable it via `BEETS_PLUGINS`, or supply its required dependencies and settings, such as a replaygain backend in `config.yaml`. Extra plugin dependencies need a custom Docker image. |
| `docker compose pull` 404 | Image not published under that tag yet. [Build from source](../README.md#development). |
| Healthcheck failing but port reachable | `/healthz` only proves the process is alive; Docker checks `/readyz`. A failing readiness check means the saved login, data directory, Queue/History database or run lock is unsafe, or the app is shutting down. Check `docker logs qobuz-librarian` and **Settings → Diagnostics**. Read-only music or staging volumes report degraded but stay healthy. |
| Upgrade fails with `Permission denied` backing up an album | An earlier `docker exec … beet …` ran as root, leaving root-owned files `PUID 1000` cannot move. Rerun with `docker exec --user 1000:1000 …`, or `sudo chown -R 1000:1000 ./music`. |
| Files vanished from `/music` after a manual `beet` command | `beet -d /config/beets …` reads `-d` as the destination, so with `move: yes` it relocates the library into the config volume. The container already exports `BEETSDIR`; run `beet …` with no `-d`. |
| `curl` / `cp` / `mkdir` misbehave on Windows | PowerShell's `curl` is an alias for `Invoke-WebRequest` with different flags, and chained commands do not behave the same. Run the setup in WSL or Git Bash. |
